solomon 서비스에서 채팅을 비동기으로 구현할 시 치명적인 엣지 케이스

메시지가 채팅 서버에 도착하면 웹소켓을 먼저 쏘고 채팅 메시지를 비동기로 저장한다고 했을 때,

처리량이 많아져 db에 병목이 생겼고, 상대방은 오프라인이라 웹소켓으로 메시지를 못 받았다.



이후 상대방은 재접속 및 채팅방 최근 메시지 내역을 불러왔고, 그동안의 메시지는 아직 db에 없다.

비동기라 실시간성은 유지돼서 과거 히스토리를 최신 내역이라고 믿은 맥락이 깨진 채로 유저가 실시간 채팅을 이어간다.



위 상황은 비동기식 채팅을 내 서비스에 적용했을 때 충분히 발생할 수 있는 아주 치명적인 시나리오다.

solomon 서비스에서 발생하는 모든 채팅은 자잘못을 가리는 싸움 상황이다. 

이러한 전제 조건에서 위 엣지 케이스는 사실상 서비스의 실패나 다름없다.



해결법: 채팅방 메시지 처리 -> 웹소켓 fanout 동기식 전환

low latency를 포기하고 웹소켓 fanout 전 채팅 메시지 관련 작업을 처리하면 해당 문제를 원천 차단할 수 있다.



채팅 메시지 관련 작업이란 채팅 메시지가 발생하면 따라오는 여러 파생 작업을 의미한다.



예를 들어, 

채팅 메시지가 발생하면 해당 채팅방에 참여중인 유저들의 채팅 목록에 해당 채팅방이 상위로 정렬돼야 한다.

채팅 목록에서 보여줄 미리보기 카드에 마지막 메시지 정보(내용, 시간), 안 읽은 개수 등도 업데이트돼야 한다.



채팅방 메시지의 경우 사용하는 인덱스 해봤자 시간순 정렬이라 항상 증가하니 인덱스 트리의 마지막에 '삽입'만 하면 돼서 빠르지만

유저별 참여중인 채팅방 정렬은 인덱스 삭제, 위치 탐색, 삽입을 동반하기 때문에 '상대적'으로 오래 걸린다.



따라서 채팅방 메시지만 동기식으로 처리하고 파생 작업은 비동기로 하면,

채팅 중 메시지 조회 불일치를 해결하면서 최대한의 속도를 낼 수 있다.



한계 돌파: lsm-tree로의 전환  

b-tree는 읽기에 최적화된 자료구조다. 반면 lsm-tree는 쓰기에 최적화된 자료구조다.



rdb를 사용하는 것보다 lsm-tree를 사용해서 위의 채팅 메시지만 동기식 구조를 구현하면 더욱 성능을 향상 시킬 수 있다.



scylla db를 사용했다.

유저가 정말 많아져 동기식이라는 구조적인 문제 때문에 문제가 될 만큼 처리가 지연 될 수도 있다.

앞에서 언급한 치명적인 엣지 케이스 때문에 구조를 바꿀 수 없으니 db 처리 속도를 향상 시켜야 한다.

scylla db는 lsm-tree로 매우 빠르며 에초에 수평 확장을 전제로 설계된 db라 노드만 추가하면 샤딩이 가능하다. 



진행중인 재판의 채팅방 메시지(핫 데이터)는 쓰기에 최적화 된 scylla에 동기로 쓰고, 읽는다.

종료돼서 더 이상 채팅이 발생하지 않는 채팅방 메시지(콜드 데이터)는 rdb로 옮겨 놓고 읽기에 최적화된 rdb에서 읽는다.



여러 db 운용 디테일

메시지는 scylla, 파생 작업은 mysql에서 진행했다.



메시지 처리 컨슈머에서 scylla에 저장하고 웹소켓을 fanout 하고

이벤트를 발생시켜 별도의 컨슈머가 mysql에 파생 작업을 처리한다고 했을 때

컨슈머 <-> 이벤트 브로커 간 간 짧은 네트워크 문제 등 이벤트 발행이 실패하는 경우도 생각해야 했다.



컨슈머에서 재시도를 한다면 다음 메시지 처리가 늦어지고 메시지가 쌓여 결국 채팅 latency가 증가한다.



따라서 이벤트 발행 작업을 없애고 outbox 패턴이나 scylla cdc를 이용해야 한다.

scylla는 멀티 파티션 acid 트랜잭션이 불가능하기 때문에 scylla cdc를 이용했다. 



반대로 재판 도메인 행위는 mysql에서 먼저 진행한다.

재판 도메인의 행위 하나 하나가 

~~님이 의견을 제출했습니다와 같이 시스템 채팅 메시지를 동반하고

채팅 메시지는 scylla에서 읽기 때문에 mysql 작업 이후에

scylla에 반영해야 한다.



재판 의견 제출 등은 채팅에 비해 빈도수가 매우 낮고 찐빠가 나면 안 되기 때문에

트랜잭션이 강력한 mysql에서 진행하고 시스템 메시지만 scylla에 올리기로 했다.



latency보다는 정확성이 훨씬 중요하고 누가 재판 준비 완료 작업을 완료했는데

시스템 메시지에 ~~님이 재판 준비를 마쳤습니다. 의견을 제출해 주세요. 시스템 메시지가 안 오면

재판 진행 자체가 안 된다.



따라서 mysql 작업 -> scylla 시스템 메시지 insert는 절때 소실되면 안 된다.



이 구조에서 mysql 작업 후 scylla 시스템 메시지를 동기적으로 한 스레드에서 처리하면

네트워크 찐빠같은 이유로 scylla가 실패했을 때, 해당 스레드에서 재시도를 해야 한다.



latency가 중요한 작업은 아니라 괜찮아 보일 수 있지만, 만약 애플리케이션 서버 장애 시

scylla 작업이 아예 소실돼버린다. 따라서 이 케이스도 마찬가지로 outbox 패턴 or cdc를 사용해서

eventually consistency 하게 만들어야 한다.



mysql은 cdc도 지원하고 다중 테이블 트랜잭션도 가능하기 때문에 outbox도 가능하다.



이건 outbox로 했다. scylla cdc는 scylla가 멀티 파티션 원자적 트랜잭션이 안 되기 때문에 강제로 한 거지만

mysql cdc까지 도입하면, 재판 도메인 행위가 준비, 의견 제출, 판결 이 세 개 밖에 안 되기 때문에

debizium까지 도입하기에는 시스템 복잡도가 커진다고 생각해서, 별도 인프라 확장이 필요 없는 outbox 패턴을 선택했다.



파생 작업 fanout-write vs fanout read

scylla에 메시지를 먼저 쓰고 

비동기로 mysql에 파생작업을 하는 거다. 



여기서 파생 작업은 말했지만

채팅방 활동순 정렬, 채팅방 미리보기 데이터 최신화를 말한다.



두 가지 방법이 있다.



1. fanout read

메시지를 읽으면 

채팅방_유저 테이블에 읽은 seq or 읽은 시각을 저장한다.



scylla cdc로 메시지가 추가되면

mysql 채팅 메시지 테이블에도 메시지를 추가한다.



조회할 때 

채팅방 정보(제목, 재판 상태) 활동순 20개, 채팅방 메시지 테이블 마지막 채팅 메시지, 채팅방_유저 테이블 읽은 seq를 join해서 가져오고

마지막 채팅 메시지 seq 컬럼이라 읽은 seq를 뺀다.



쓰기를 읽을 때 1번, 메시지 쓸 때 1번 하고 읽기를 복잡하게 하는 방법이다.



2. fanout write

아예 비정규화 채팅방 미리보기 카드 테이블을 만들고



메시지를 읽으면 

그 유저의 비정규화 테이블 row에 읽은 seq 컬럼을 업데이트한다.



채팅이 발생할 때마다

채팅방 유저들의 비정규화 테이블 row에 메시지 정보(내용, 시간, seq)를 업데이트한다.



조회할 때

그냥 바로 메시지 보낸 시간 별로 20개 짤라서 가져오고 총 seq - 읽은 seq를 쳐버리면 된다.



채팅방 유저 N명에 따라 n번 fanout write 비용이 발생하지만 읽기는 1번으로 고정된다.



3. 나의 판단

fanout read.

조회는 복잡하나 mysql에 메시지 row만 하나 추가하면 되기 때문에 쓰기는 쉽다.

이것보다 더 큰 이득이있다.

일단 mysql에도 메시지가 다 저장되기 때문에

진행중인 재판 데이터는 scylla에서 지연없이 읽고

끝난 재판 데이터, 콜드 데이터는 mysql에서 읽어와 scylla 부하를 줄여 latency를 최대화 할 수 있기 때문이다.



또한 추후 일대일 채팅이 아닌 다수가 참여할 수 있는 채팅으로도 확장할 수도 있고

재판 진행 상태에 따라 미리보기 카드 ui를 바꿔서 보여줘야할 수도 있다.

이때 비정규 방식은 채팅 발생 뿐만 아니라 재판 단계가 바뀔 때도 모든 유저의 미리보기 카드도 업데이트 해줘야 해서



fanout read가 합리적이라고 생각했다.
